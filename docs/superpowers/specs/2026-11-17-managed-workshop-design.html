01 / THE PROPOSAL

Keep the choice with the application owner.

During setup, an owner chooses how the generated application will execute work. Responses API — application managed retains the current chat and tool loop. Agents API — OpenAI managed introduces managed sessions and an optional working environment for extended tasks and file deliverables. The generated application remains standalone in both cases.

The two runtimes share the product shell: application identity, instructions, file intake, knowledge bindings, tool permissions, status, history, version display and export workflow. Each runtime implements its own provider protocol behind a common interface.

Existing path · preserved

Responses API

Studio owns the model/tool loop and local conversation state. Suitable for direct answers, knowledge questions and bounded workflows. Fixed and Auto model selection remain available.

New path · proposed

Agents API

OpenAI owns the agent loop and provider session. Studio owns the application experience, custom function handling, access checks and local run records. Start with one agent and an OpenAI-hosted workspace.

The Agents API provides managed orchestration and environments, but application servers still supply their custom function handlers. That is the responsibility boundary this design follows. OpenAI: architecture.

Two separate choices

Runtime determines who manages execution. Model policy determines which eligible model performs it. The Decisions API classifier does not choose the runtime, grant permissions, or replace the agent loop in this first release.

02 / SCOPE & ALTERNATIVES

A shared core, two runtime adapters.

ApproachTradeoffRecommendation
Retain Responses onlySmallest change, but Studio must build every additional orchestration capability itself.Maintain as the default and baseline.
Replace everything with AgentsIntroduces managed sessions to simple apps, changes storage and costs, and risks compatibility regressions.Do not make this the migration strategy.
Shared core + explicit runtime adaptersRequires a capability matrix, lifecycle normalization and testing for both paths.Recommended proposal; pending your approval.
Use Agents SDK for a caller-owned loopUseful when Studio needs to own agent orchestration, but adds another execution approach.Defer. The first implementation uses the Agents API directly.

Initial delivery boundary

Enable the runtime selector in Studio and export both kinds of applications. Deliver reliable single-agent work, a recoverable task timeline, file outputs, reviewed read-only tools, knowledge retrieval and evaluation gates. Retain the existing conversational setup interpreter on Responses.

Separate later work

An agent that generates tailored frontend source is a later builder enhancement, not a prerequisite for running generated apps on Agents. Also defer multi-agent delegation, schedules, automatic runtime switching, arbitrary remote MCP servers, browser/computer use, self-hosted sandboxes and write integrations. The private experience designer and its SSO are not implicitly merged into the public product.

Implementation destination is a review decision. This document uses the public repository as its inspected baseline; approval must specify whether the work belongs in public ai-app-studio, private ai-app-studio-next, or a staged port.

06 / EXECUTION & RECOVERY

A run has a lifecycle beyond a browser connection.

  1. Preflight. Validate runtime, model configuration, tool capabilities and limits. Verify provider access through an explicitly initiated bounded test during setup; never infer access from a saved API key.
  2. Record intent. Create a local run with a unique submission ID before contacting the provider. Persist the configuration fingerprint. Permit one active turn per conversation; independent conversations use separate run locks.
  3. Create or continue. Use the typed client.beta.agents session interface. Persist provider session/turn IDs as they become available. Never send a normal follow-up as new input while a turn is active: the provider treats active-turn input as steering.
  4. Observe and execute tools. A server-side supervisor receives events and handles pending functions independently of the browser. Deduplicate functions by session, turn and call ID. Save each validated result before returning it. Require replay-safe read handlers; an execution that succeeds before its result commits can still be ambiguous. Retry only replay-safe reads, and leave non-replay-safe outcomes in an explicit reconciliation state rather than claiming exactly-once execution.
  5. Reconcile. After a disconnect, reconnect the event observer before retrieving saved items and turn status. Provider streams do not replay missed events. Deduplicate local records and reconstruct the visible timeline from saved state.
  6. Finish. Mark completion only after the intended turn’s terminal outcome is confirmed. Retrieve and validate its artifacts, store local copies, then emit a saved completion receipt to the browser. Session idle alone is insufficient.
  7. Cancel or recover. A cancel request moves to “Cancelling” until acknowledged. On server restart, recover active run records and pending calls. If initial submission had an ambiguous outcome before IDs were saved, mark “Needs reconciliation”; do not automatically resubmit. A durable session does not preserve an expired workspace. Retain original attachments until the run’s recovery window ends; if compute expires, recover supported saved outputs and require a new conversation with explicitly re-staged inputs when the workspace cannot be resumed.

Provider behavior: sessions and reconnection, pending function actions, failure recovery.

Normalized user-visible states

queued → preparing → running ↔ waiting_for_tool → finalizing → completed, with explicit branches for reconnecting, cancelling → cancelled, failed and needs_reconciliation. These are proposed Studio states, not copied provider enum values.

A closed tab does not cancel an Agents turn.

The local app server must remain available for its custom tools. If that process stops, OpenAI may continue provider-side work, but application functions can wait until recovery. Closing the browser, stopping the server, cancelling a turn and deleting a session are distinct actions.

Model routing boundary

Preserve per-turn Decisions selection and model pinning for Responses. Initial Agents sessions use an explicit fixed model and have no classifier/explanation overhead. A later Auto design must verify allowed model changes, session continuity and compatible tool sets; it must not rotate models invisibly inside a live session or silently fall back to Responses.

07 / FILES, KNOWLEDGE & TOOLS

Preserve intent at every boundary.

ConcernResponses pathProposed Agents path
Chat attachmentsKeep current inline file/image handling and history.Stage validated files into the conversation’s workspace; maintain a local-to-provider file map. No workspace requires a supported explicit input adapter.
Permanent knowledgeKeep Responses file_search and bound vector stores.Expose an app-scoped read-only search_knowledge function backed by Vector Stores search. Return bounded passages and source identifiers; preserve clickable citations.

The knowledge bridge is a new application adapter, not an assumption that Responses tool payloads work unchanged in Agents. Vector Stores supports direct semantic search; the broker must constrain stores to the app’s bound collection and prevent a model from supplying arbitrary store IDs. Retrieval guide.

Knowledge portability and revisions

Exports contain vector-store references, not the knowledge corpus or its credentials. They work only with an API project authorized for those stores. A first-start check verifies access; a different project requires an explicit re-upload/rebind step. Record a collection revision or inventory fingerprint at conversation start. Detect owner-managed changes before follow-ups and require a new conversation; out-of-band remote changes cannot be guaranteed detectable, so reproducible evaluations use dedicated frozen collections. Citation links resolve through the app server and its ownership checks, never raw provider URLs or arbitrary file IDs.

Limits and resource handling

Retain the framework’s existing intake ceiling: 5 files per message, 10 MiB each, 20 MiB combined per message and conversation, with the existing supported-extension allowlist. Apply tighter provider/transport constraints when needed and explain them before submission. Use supported Files API references when inline environment upload limits are insufficient; do not truncate a document silently. Keep private filenames sanitized, paths under the assigned workspace and each upload mapped to its originating conversation.

Stage inputs with the environment file interfaces and retrieve outputs using the provider artifact interfaces. Each output must match its session, completed turn and path before download. This design proposes a separate default artifact ceiling of 25 MiB per file and 100 MiB per run, configurable within provider limits. Block executable and active HTML/SVG previews; download allowed files with safe content types and attachment headers. Provider file/artifact contract.

Permissions and retention

The API key stays on the application server and outside the sandbox. For the initial file-workflow profile, explicitly set sandbox outbound network access to disabled; any later network-enabled profile needs reviewed exact-host restrictions. Do not mount host directories or inject application credentials. Allow sandbox-local code execution and file writes needed for deliverables, with pinned required packages. Set session review: "auto_review" explicitly and include reviewer usage in accounting. This is provider automatic review, not a manual business-approval flow. A Tool Broker allowlist alone cannot constrain shell network access. Sandbox permissions and automatic review semantics inform these controls. External write tools remain disabled initially; local generation of an output file is allowed. A future write tool requires an explicit approval and idempotency design.

Agents introduces provider-stored sessions and artifacts alongside local state. Existing Responses store: false semantics cannot be carried over as a privacy promise. Present that difference in setup. Proposed defaults: retain local artifacts and inactive provider sessions for 7 days; do not delete active work; offer “Delete conversation and provider resources” with a cleanup ledger and retryable failure states. Shared knowledge collections are never deleted by conversation cleanup. Users can choose longer retention; no automatic claim of zero retention or encrypted local storage.

Cleanup inventory and offline behavior

The seven-day inactivity proposal covers session-owned source uploads, workspace copies, local input binaries, local artifacts, safe replay events and cached tool results. Track every created remote file ID and whether it is shared; delete only resources owned by that session. Preserve the local conversation transcript and compact receipt under the existing owner-controlled history policy, marked archived when its provider session expires; continuing requires a new session. A stopped local server cannot enforce scheduled cleanup: show overdue resources and reconcile them at next startup. Trace retention and provider service logs follow project/provider controls rather than the local timer. “Deletion requested” and “provider deletion confirmed” are distinct; neither promises immediate physical erasure. Session management.

08 / CONFIGURATION & INTERFACES

Make runtime choice portable and versioned.

Introduce app schema 2.0, with a compatibility reader for existing schema 1.0. Normalize legacy apps to Responses in memory; do not rewrite their source automatically. New exports declare the runtime explicitly. The following is a proposed Studio manifest fragment, not a provider request:

{
  "schema_version": "2.0",
  "runtime": {
    "api": "agents",
    "model": "gpt-6-astra",
    "routing": null,
    "agents": {
      "environment": "openai_hosted",
      "network_access": "disabled",
      "review": "auto_review",
      "tool_policy": "read_only",
      "max_run_seconds": 300,
      "max_application_tool_calls": 12,
      "artifact_retention_days": 7
    }
  }
}

The model is an illustrative documented example, not an access guarantee. The proposed five-minute run deadline and twelve application-tool calls are initial configurable defaults. A deadline requests cancellation; it is not a hard provider-side spend cap. Sandbox commands and internal model work are not counted as application function calls.

Shared runtime interface

Define application-owned methods validate_config, start_turn, observe_run, get_snapshot, cancel_run, list_artifacts and delete_resources. Responses preserves its current synchronous lifecycle behind the adapter. Agents supplies managed-session semantics. Unsupported operations are declared through capability flags rather than emulated with hidden provider calls.

Application routes and events

Keep existing chat/session endpoints working for legacy clients. Add proposed GET /api/runs/{id}, GET /api/runs/{id}/events, POST /api/runs/{id}/cancel and GET /api/artifacts/{id}/content. New browser requests carry a stable submission ID. These are Studio routes, not OpenAI endpoints.

Version the browser event envelope with run ID, local event sequence, type and payload. Preserve current routing, delta, status and done behavior; add explicit task-state and artifact events. A new browser can replay locally persisted safe events by sequence and reconcile a snapshot; it never assumes the provider replays events.

Persistence and observability

Add runs, provider_sessions, tool_calls, artifacts and cleanup_jobs records in the local SQLite data folder. Store app/conversation ownership, config fingerprint, session/turn/call IDs, lifecycle timestamps and terminal outcomes. A uniqueness constraint protects each submission and tool call. Store file contents in a private filesystem directory with DB metadata, not in exports.

Routing status shows the runtime, orchestration owner, fixed/Auto model policy, task state and current model. Keep classifier, explanation and answer usage separate on Responses. Show Agents run usage and tool/environment components when available; mark pending/unknown values rather than guessing a dollar total. Add trace references to the run receipt; provider trace export requires organizational enablement and suitable permissions. Tracing reference.

09 / IMPLEMENTATION PLAN

Ship in slices, with a compatibility gate.

0

Approve scope and destination

Review this document and the mockups. Select the implementation repository, initial environments and tool coverage. No framework implementation begins from this Site alone.

1

Extract the runtime boundary

Refactor gptapps/runtime.py behind the shared adapter interface. Add a Responses adapter with unchanged behavior, schema compatibility in spec.py, capability reporting and regression fixtures. Exit: existing app, attachment, routing, streaming and export checks pass.

2

Prove one managed session

Add an optional pinned OpenAI Python SDK dependency supporting the public beta.agents surface. Keep Responses-only installs lightweight. Implement one fixed-model hosted session, output streaming, IDs, cancellation, completion verification and a single downloadable text/PDF artifact. Use a user-approved key only for a bounded live verification.

3

Make it recoverable

Add the run database, server-side task supervisor, per-conversation leases and startup reconciliation. Implement pending-function recovery, local event sequencing, duplicate submission protection and a cleanup worker. Exit: browser disconnect and process restart preserve run identity, reuse committed tool results and reconcile ambiguous outcomes.

4

Bridge real application capabilities

Adapt validated attachments, bound knowledge search, citation rendering and registered read-only handlers. Add output validation, download isolation, retention controls and a tool-compatibility report. Each enabled capability needs an end-to-end test; missing parity blocks that configuration.

5

Integrate setup and standalone builds

Extend setup.py, web.py, chat.html/js/css and the routing panel for runtime selection and task states. Update build.py’s explicit copy list, runtime-specific dependency manifests, launchers and Docker templates. Stamp the version/build at bottom-left. Add both architecture diagrams and runnable examples to README/release notes.

6

Evaluate, release selectively, then expand

Run the common task suite against both runtimes and the fixed-model baseline. Record instruction/tool/source versions, outcomes, latency and total usage. Release Agents as opt-in only after agreed checks pass. Later proposals can add Agents Auto, multi-agent specialists, approved writes, self-hosted environments and a UI-generating build agent.

Packaging and operation

Generated Agents apps include the adapter and their own supervised run service; they do not depend on a running Studio. The start scripts install/verify compatible Python dependencies and open the correct URL. Docker supplies the application server’s Python; the OpenAI-hosted sandbox is a separate environment with its own package configuration. Mount the private data directory persistently, and handle shutdown without reporting unfinished tasks as completed.

No delivery-date or operating-cost estimate is committed before the access/compatibility spike. A managed harness can reduce orchestration code while introducing provider state, compute and operational costs.

10 / EVALUATION & ACCEPTANCE

Prove behavior, not just a successful API call.

Maintain a versioned evaluation set covering document review, sourced Q&A, constrained transformation and a task producing an artifact. Include representative attachments, ambiguous requests, malicious document instructions and unsupported tools. Compare against the current fixed-model Responses baseline; evaluate the full workflow as well as its answer. Calibrate automated graders against human review. Evaluation guidance.

GateRequired evidence before release
CompatibilityLegacy manifests and exported apps pass existing checks; runtime/model settings survive save and export; unavailable tools block clearly.
LifecycleCompletion, failure, timeout, cancel race, disconnection, restart and unknown-submission outcomes have tests. Deduplicated committed results, replay-safe reads and explicit handling of the execute-before-commit crash window.
Sources & instructionsReviewed answer correctness, instruction following, source grounding and citation fidelity meet a pre-agreed task rubric.
ArtifactsOpen every expected file, inspect content, and verify conversation/turn ownership. A completed run with missing or invalid files is not presented as a complete deliverable.
Access & boundariesNo cross-app or cross-conversation access, path traversal, key exposure, unauthorized tool or executable preview. Verify any private-repo identity integration separately.
Quality & efficiencyCompare task completion, retry rate, latency and total model/tool/environment usage. Define numeric release thresholds with the owner after establishing the baseline.
Packaging & UIClean local and Docker starts for both runtimes; responsive, keyboard and screen-reader flows; safe Markdown rendering; bottom-left version/build.

Use deterministic fake-provider tests for protocol handling and failure injection. Run bounded live contract checks to confirm actual access and behavior, then behavioral evaluations using approved representative data. Mock tests alone cannot establish model quality. Log safe structured metadata by default; enable sensitive payload capture only through an explicit retention policy.

Evaluation is a separate framework component.

Agents traces help investigate execution; they do not automatically implement production evaluations, authentication or support ownership. Model, instruction, tool and routing-policy changes all trigger the agreed evaluation suite and have a rollback path.

11 / DECISIONS FOR YOUR REVIEW

The choices to settle before implementation.

The following defaults are recommendations, not decisions already made on your behalf.

  1. Repository: implement first in public ai-app-studio, private ai-app-studio-next, or develop privately and port a reviewed shared runtime?
  2. First release: approve two explicit runtimes, Responses as the default, and fixed-model Agents sessions initially?

  4. Permissions: retain read-only business tools and defer external write actions, multi-agent delegation and arbitrary MCP connections?
